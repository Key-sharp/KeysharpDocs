Platform Support

The parser, compiler and general runtime operate on Windows, Linux and macOS. Features which integrate with windows, input devices, the screen, desktop services or native APIs can require platform-specific backends or permissions.

Note: This page describes shared platform requirements. Each function page describes the observable contract and limitations specific to that function.

Windows

Windows currently has the broadest AutoHotkey v2 compatibility. Windows integrations use native Windows APIs and WinForms.

The main general differences are:

  • Object destruction is non-deterministic because objects follow the .NET garbage-collection model. See Object Lifetime.
  • GUI rendering uses WinForms. Controls can differ in default size, Z-order and label rendering, and a GUI can appear blank before it has first been shown because WinForms initializes controls lazily.

Registry functions are available only on Windows. The COM functions are available on all three platforms, but only Windows drives real COM: see Interprocess automation with ComObject on Linux and its macOS counterpart.

Permissions

keysharp-input owns the privileged input service. A system installation of keysharp-desktop owns the per-user desktop service and a root authority. Applications use stable client libraries rather than the private socket protocols. When a permanent per-application grant is missing, the responsible system component asks polkit to authenticate the active user. Denials and cancellations are not stored.

The system components are independently installable and share the root-owned grant store under /var/lib/keysharp-permissions/v1. InputControl is shared and can be managed by either component; InputMonitoring belongs to keysharp-input, and the desktop capabilities belong to keysharp-desktop. Cursor position, modifier state and lock-toggle state are ungated. List grants with keysharp-input permissions list or keysharp-desktop permissions list. Revoke one with keysharp-input permissions revoke --hash <hash> input-monitoring or keysharp-desktop permissions revoke --hash <hash> screen-capture; each command's help lists its other targets and scopes.

A source-built per-user keysharp-desktop installation instead uses a local dialog and a private user grant store. It records consent but cannot isolate its grants from other processes running as that user, does not authorize the system keysharp-input service, and yields to a running system desktop authority.

Joystick discovery and state reads do not use keysharp-input. They access evdev directly and can require membership in the input group.

Controls and accessibility automation

Control functions operate on controls belonging to windows created by the current script. Linux desktops do not expose foreign application controls through the same model as Windows.

For cross-process inspection and automation, use AtSpi.ks. Running it directly opens AtSpiViewer; the library also provides APIs similar to Windows accessibility and UI Automation libraries.

Registry functions are unavailable on Linux. GUI support is broadly implemented, although individual control pages identify missing or differing behavior.

Interprocess automation with ComObject

ComObject addresses a D-Bus service, which fills the role COM automation fills on Windows: a named service exposes objects whose methods, properties and signals a script calls by name. The COM function names are kept so that the automation surface reads the same on every platform, as DllCall does; the target strings themselves are not portable between platforms.

A target is written [session:|system:]service.name[:/object/path]. The session bus is used unless system: is given. When the object path is omitted it is derived from the service name by replacing each dot with a slash; if no such object exists, the error names the objects the service does expose.

Members are resolved through D-Bus introspection, so a service must be introspectable. When a member name appears on more than one of an object's interfaces, pass the interface name as the second parameter of ComObject, or select it with ComObjQuery.

D-Bus is strictly typed on the wire and performs no implicit conversion. Argument types come from the service's own introspection data, so ordinary calls need no annotation; use ComValue where a type cannot be derived from it, most often for the values of an a{sv} dictionary.

Note: Functions which depend on COM machinery that D-Bus does not have throw an error stating the reason rather than failing silently: ComCall (no virtual function tables), ObjAddRef and ObjRelease (no reference counting), and ComObjValue, ComObjFlags and ComObjFromPtr (no interface pointers or VARIANT flags). ComObjArray does not exist on Linux, so referring to it is a compile-time error.

Interprocess automation with ComObject

ComObject addresses a scriptable application through Apple Events, which fills the role COM automation fills on Windows: an application publishes a scripting dictionary whose commands, properties and elements a script uses by name. The COM function names are kept so that the automation surface reads the same on every platform, as DllCall does; the target strings themselves are not portable between platforms.

A target is an application, written as a bundle identifier ("com.apple.Finder"), a name ("Finder"), a bundle path, or "pid:1234", which addresses that process rather than whichever instance the bundle identifier currently resolves to. ComObject launches the application if it is not running, without bringing it to the front; ComObjActive and ComObjGet attach to a running one and throw otherwise.

An Apple Events object is a query rather than a handle. window 1 of application "Finder" is resolved by the application each time it is used, so narrowing a collection costs nothing until a value is actually read, and an object which has become stale fails when it is used rather than when it was created.

Members are resolved through the application's scripting definition, whose terms contain spaces. Spaces and underscores are folded away and case is ignored, so a term such as file name is reachable as FileName, filename or file_name. Where two suites define the same name with different events, the error lists them; pass the suite name as the second parameter of ComObject, or select it with ComObjQuery.

Apple event parameters are addressed by keyword, so the first unnamed argument is the command's direct parameter and every other value is passed by name: win.Close(Saving: "no"). When the receiver is an object rather than the application itself, the receiver is already the direct parameter, so supplying another unnamed argument is an error.

Controlling another application requires Automation permission, granted per target application in System Settings → Privacy & Security → Automation. Permission is requested before the first event so that the prompt is attributed correctly. This is separate from the Accessibility permission the window functions use.

Note: Functions which depend on COM machinery that Apple Events does not have throw an error stating the reason rather than failing silently: ComCall (no virtual function tables), ObjAddRef and ObjRelease (no reference counting), and ComObjValue, ComObjFlags and ComObjFromPtr (no interface pointers or VARIANT flags). ComObjArray does not exist on macOS, so referring to it is a compile-time error.
